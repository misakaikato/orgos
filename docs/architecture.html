orgos 架构

人与各自的代理组在同一个即时通讯里协作：分身对外代表本人，助手替本人干活，设备 Runner 把员工电脑变成虚拟总线上的节点。下面先总览，再逐层展开：系统分层、服务端模块地图、分身怎么处理一条消息以及它在代码里走过的路径、会话内话题、设备 Runner 与外部 agent、企业模型网关、记忆层、数据模型、连接与协议，最后是关键决定与进度。

一条消息怎么被分身处理

以许诺在私聊里问林晓为例。私聊里同时有林晓本人和她的分身；分身只在三种情况下开口，开口后先查记忆、再判断是否在授权内。

同一条消息在代码里走过的路径

还是许诺问林晓的例子，这次问的是订单服务切流什么情况下重新评估。下图按时间从上到下，列出每一步经过的模块；蓝色虚线是经网关的模型调用，灰色虚线是返回。

一个代理，多条线：会话内话题

每个代理和本人只有一个私聊，列表里只占一行。私聊里分话题，每个话题是一份独立上下文，外部 agent 每个话题对应一个自己的会话；任务就是带状态的话题。

设备 Runner 与外部 agent

员工电脑上跑一个 Runner：它主动连回服务端，执行四项设备能力，并用 ACP 驱动本机的 Claude Code、Codex 等外部 agent。每个话题对应一个 ACP 会话。

企业模型网关

本租户所有模型调用的唯一出口。服务端自己的代理引擎和企业模式下的外部 agent 走同一个函数，所以计量只有一处。

记忆从哪来、到哪去

不需要对分身说"记住"。原始证据本来就在存，记忆整理在会话告一段落、任务结束时自动提炼；本地 agent 做过的活随任务的过程记录一起进来。

数据模型

PostgreSQL 16，32 张表分五组。每张表都带 tenant_id，按租户隔离；events 与 task_logs 只追加。

上报的可靠性不靠提示词：为他人办事时回复声称"已转交"而本轮没调用上报工具，运行循环拦下并纠正一次规格"上报的运行时校验"

走向正式产品

MVP 验证了四种沟通、部门、设备、外部 agent、记忆与"指挥代理操作软件"能在一套系统里成立。正式产品建议保留骨架、替换实现：下面第一张表是经过验证、值得原样带走的设计；第二张是 MVP 为了快而做的简化，正式开发时要重做；最后是具体的技术债。

值得原样带走的设计

设计为什么值得保留代码位置
主体模型人、代理、部门都是主体；代理必有一个本人（人或部门）。分身、助手、部门分身、外部助手都是同一套机制的实例，权限与上报沿同一条链走db/schema.ts principals · services/units.ts deciderOf
事件只追加、唯一写入口所有会话里发生的事都是一条事件，只经 services/events.ts 写入；代办标记也只在这里把 actor 改记为代理。审计、推送、提炼都从事件派生services/events.ts
话题是上下文边界每次代理运行只读本话题，外部 agent 每话题一个会话；任务是带状态的话题。长对话靠检查点压缩，跨话题只给近期简报agent/context.ts · services/topics.ts · runs
协议包是单一真相源REST 出入参、推送帧、Runner 帧、ACP 适配器表、厂商预设、记忆类别都是 Zod 模式，前端、服务端、Runner 共用，只增不改packages/protocol
企业模型网关三种入口协议 × 三种上游协议，经统一中间结构互转；计量、限额、审计天然只有一处；外部 agent 只拿随会话吊销的任务令牌gateway/*
Runner 主动连出 + ACP员工电脑不开端口、不组网；子进程环境清洗，厂商 key 永不下发；外部 agent 靠 ACP 接入，换 agent 只加一行适配器apps/runner · protocol/acp.ts
记忆的可见性可见范围由来源决定，过滤只在一个函数；类别授权 + 第三人规则 + 代答记录与更正，让"替我说话"可控可追memory/access.ts
能力随接口增长代理操作软件走同一套接口与权限；接口目录有完整性测试，新接口不登记就过不了测试agent/app-api/catalog.ts
三层测试集成测试连真库、端到端脚本用确定性假模型、真实模型冒烟单独跑；假模型指令让端到端可复现apps/server/tests · scripts/e2e.ts · smoke-llm.ts

MVP 的简化，正式产品要重做

方面现状与问题建议
单进程内存状态浏览器与 Runner 连接表、调度队列、外部会话槽、记忆作业执行器都在进程内存里，只能跑一个实例，重启会丢排队中的运行调度与作业进持久队列（Postgres SKIP LOCKED 起步），连接与推送经消息总线跨实例路由，会话槽落库；见上图
可靠性靠提示词模型遵守规则不稳：上报调了 6 版提示仍会口头声称已转交，最后靠运行时校验兜住；部门分身会合理化越出章程关键行为一律"工具调用 + 服务端校验"；建真实模型评测集（smoke 为起点），每次换模型或改提示都回归
检索应用层按字二元组打分，没有索引，数据一多就慢、召回弱Postgres 全文与 trigram 索引，再加向量检索（列已预留）
身份与组织只有邮箱密码登录；部门树只有接口，没有管理界面SSO（OIDC/SAML）、SCIM 目录同步、多因素认证；组织管理后台
权限与隔离角色只有租户 owner、成员、部门负责人；隔离只靠应用层 scoped(tenantId)RBAC 或策略引擎；数据库行级安全作第二道防线
密钥厂商 key 用单一 ORGOS_SECRET 派生的密钥加密，换密钥要重填接入 KMS，按租户数据密钥，支持轮换
代理代办不确认本人的代理以本人权限直接操作，群里别人的话会进它的上下文，存在提示注入风险social_write 默认确认或做异常检测，按租户可配；敏感接口加二次确认
记忆分类靠模型私事可能被错分成可对外类别；提炼偶尔写错日期；部门内部资料可经协商内容流出拿不准一律归私人事务；本人审阅入口；敏感类别二次校验；资料加"仅部门内"标记并在对外时强制过滤
可观测与合规日志只到标准输出，有运行记录与计量但没有指标、追踪和审计界面；没有数据保留、导出与删除指标与链路追踪、模型调用看板、审计查询界面；按个人信息保护法做保留期、导出与删除
部署形态只有本地开发形态（Next 开发服务经服务端反代）生产构建与容器化，明确 Web、接口、实时网关的部署拓扑与迁移流程
桌面客户端未签名、无自动更新，Runner 由 app 看护，只在 macOS 验证；安装包 150MB签名与公证、自动更新、可选系统级后台服务、Windows/Linux 验证；体积敏感时评估 Tauri
功能缺口没有文件与附件、邮件、工作台、移动端、跨公司协作；外部 agent 还不能调用 orgos 自身的能力按优先级补；外部 agent 经 MCP 复用同一份接口目录

技术债清单

  • 真实模型实测里，同一次"问部门"按会话统计 5 次模型调用、按运行统计 6 次，差的一次没有查清
  • 画像重建在相邻两次轮询里对同一人各跑一次，重复计费
  • 分身转告本人答复时会模仿历史消息格式，带上"【许诺】"前缀；回复里会把群 id 直接念出来
  • 代办标记会被请求期间派生的后台任务继承（只影响 actor 等于本人的事件）
  • 应用接口调用的过程记录挂在运行名下，不在任务过程视图里
  • 代理代发的消息不触发任何代理（有意为之，防止自我打断），因此"转为任务"后被交办的代理不会自动开始
  • 端到端脚本为跳过 10 分钟去抖直接改了提炼作业的执行时间
  • 编译版 Runner 里测试用的 fake 适配器不可用；desktop:dev 会清空已打好的安装包
  • 模型的日期与假期推理会出错（把 9 月 29、30 日当成国庆假期），章程边界会被模型自行放宽（研发部接受了周五）
