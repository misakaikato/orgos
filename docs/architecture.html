orgos 架构

人与各自的代理组在同一个即时通讯里协作：分身对外代表本人，助手替本人干活，设备 Runner 把员工电脑变成虚拟总线上的节点。下面依次是：系统分层、一条消息怎么被分身处理、一个代理的多条线（话题）、记忆层，以及关键决定与进度。

系统分层

一条消息怎么被分身处理

以许诺在私聊里问林晓为例。私聊里同时有林晓本人和她的分身；分身只在三种情况下开口，开口后先查记忆、再判断是否在授权内。

一个代理，多条线：会话内话题

每个代理和本人只有一个私聊，列表里只占一行。私聊里分话题，每个话题是一份独立上下文，外部 agent 每个话题对应一个自己的会话；任务就是带状态的话题。

记忆从哪来、到哪去

不需要对分身说"记住"。原始证据本来就在存，记忆整理在会话告一段落、任务结束时自动提炼；本地 agent 做过的活随任务的过程记录一起进来。

代理与沟通方式

代理属于谁在哪运行对谁开口状态
分身每人一个服务端内置引擎本人随时；别人在私聊或群里点名、问分身、或本人忙碌时已完成
助手本人（可建多个）服务端内置引擎，可绑设备只替本人干活；被分身转交时受"为他人"限制已完成
外部助手本人设备 Runner 上的 Claude Code、Codex、pi、Hermes只替本人干活，用本人订阅或网关令牌已完成（Claude Code 真机验收）
部门分身部门（负责人拍板）服务端内置引擎任何同事可直接问；章程内自己决定，章程外上报负责人待施工

关键决定

问题决定记录
代理循环自写最小循环，不用 pi-agent-core；多厂商时再评估decisions/0001
外部 agent 怎么映射任务（A2A 状态机）+ 会话内话题；每话题一个 ACP 会话0002、0004
组织部门是主体，部门分身归部门、上报负责人；不做个人行为统计0002
模型企业模型网关：三种入口（OpenAI Chat、OpenAI Responses、Anthropic Messages）三进三出；上游支持同协议就直通，不支持就经内部统一中间结构互转（3 个解析器 + 3 个生成器，不写两两转换）；计量一处；外部 agent 默认企业模式0003
订阅只作"执行者"：由官方 CLI 用本人登录干活；不读取令牌、不转成 API0003
驱动本机 agentACP（Zed 的 Agent Client Protocol，40 多个 agent 支持）。MCP 管工具、A2A 管跨公司、AG-UI 属前端层，都不替代它；注意与 IBM 的同名协议（已并入 A2A）区分本页
设备联网保持 Runner 主动连出的 WebSocket，不组 VPN；暴露本机服务时做经这条连接的端口转发；设备间大流量阶段二再考虑 iroh 或 tsnet本页
记忆自动提炼三层；可见范围由来源决定；14 类中 6 类默认禁止对外（私人事务、薪酬、健康、家庭、人事评价、凭据与安全）；第三人私聊只转述事实、隐去来源；回答附依据；代答记录可更正；不接本地 agent 的记忆文件；先不用向量规格"记忆层"一节
