# 规格：orgos MVP 阶段一——人与代理组的即时通讯

## 背景与目标

orgos 是一个 AI 原生办公软件的实验。核心假设：每个员工配一组 AI agent（下称"代理组"），人和代理都是一等主体，信息默认先经过代理再到人。阶段一只验证四种沟通能不能在同一个即时通讯里跑通，外加让代理通过员工自己的电脑执行操作：

| 编号 | 沟通 | 验证的价值 |
|---|---|---|
| C1 | 我和自己的代理组聊 | AI 提效 |
| C2 | 我和其他真人聊 | 传统办公不退化 |
| C3 | 别人和我的代理组聊，超出授权的问题转给我本人 | 不开会也能拿到信息、推进决策 |
| C4 | 别人的代理和我的代理自动协商，结果交给双方本人确认 | 全自动沟通与决策 |
| R | 把自己的电脑配对成"设备 Runner"，我的代理能在上面读写文件、执行命令（有风险的先问我） | 虚拟总线的第一个节点 |

界面要求现代、美观、简洁易用，全部视觉决策以仓库根目录的 `DESIGN.md` 为准。另外提供一份默认演示数据和一个**模拟台**，让一个人在一个浏览器里同时扮演多个同事。

**成功标准**：`bun scripts/e2e.ts` 在无网络、`MOCK_LLM=1` 下退出码 0，覆盖 C1–C4、R 与租户隔离；接真 DeepSeek 时 `bun scripts/smoke-llm.ts` 跑通 C1 与 C3 各一轮；Web 界面上三个测试账号能手工走完全部场景。

## 非目标

- 手机端、推送、音视频、文件附件、消息编辑与撤回、已读回执、搜索界面。
- 端到端加密（本产品的组织记忆在服务端，明确不做）。
- 一个人属于多个租户（数据模型留好租户编号，但阶段一一个用户只属于一个租户）。
- 设备 Runner 上的插件、MCP、浏览器、算力共享；手机做 Runner。
- 多模型供应商切换（只接 DeepSeek，但供应商配置结构照 wisp 保留，便于后加）。
- 生成式界面、组织记忆图谱、审批引擎、定时任务。
- 生产部署、HTTPS、限流。

## 假设（施工前需用户扫一眼）

1. **两类代理**（用户已确认命名）：
   - **分身**（`role=front`，每人恰好一个，不可删除）：代表本人与**别人**沟通。怕的是说错话、乱许诺、泄露隐私；权限来自本人写的对外政策；只能用本人标为共享的资料；拿不准时转本人答复（上报卡片）；以说话为主，不直接操作设备。
   - **助手**（`role=specialist`，默认一个"执行助手"，本人可再建、改、删）：替**本人**干具体活。怕的是做错事；权限来自本人授予的工具、设备与操作级别；能看本人全部资料与自己的工作区；有副作用的操作请本人批准（审批卡片）。
   - 分身可以把别人的请求转给本人的助手，但此时助手同样处于"为他人"限制。
2. **别人找我的代理组不再是单独会话**（用户已确认）：两个真人的私聊里自动包含双方的分身。平时是人跟人聊，分身不开口；只有在(a)对方用 @ 点了我的分身，(b)对方在输入框切到"问分身"发送，或(c)我把状态设为"忙碌 / 离开"时，我的分身才替我回答对方的消息。我自己的消息永远不触发我的分身。任何人都不能单独和别人的代理开私聊。
3. **代理替别人办事时能看到什么**：只能检索本人标为"共享"的资料和记忆；本人的私聊、私有记忆、设备能力一律不可用。设备工具只在代理为本人办事时开放。
4. **协商（C4）的结构**：代理之间不发自由聊天，每一步必须调用 `negotiation_reply` 工具，带 `status`（continue/agree/reject/need_owner）和可选的 JSON `proposal`；对方用 `agree` 回应同一个 proposal（深度相等）即达成。最多 8 步。
5. **群聊里多个代理的发言规则**照 Lorca：被 @ 的先说，其余按入群顺序各轮到一次，可以无声跳过；有人发言才进下一轮，只点听到新内容的代理；最多 4 轮；人发新消息会结束当前这一轮。
6. **一个用户只属于一个租户**；注册时要么新建组织，要么用邀请码加入。
7. **代理引擎自己写一个最小循环**，不用 pi（理由见 `decisions/0001-agent-loop.md`，施工第一步写入）。

### 代理引擎（`apps/server/src/agent/`）

**LLM 客户端**（`llm.ts`）：OpenAI 兼容 Chat Completions，`stream: true`，`stream_options.include_usage`，对 DeepSeek 带 `thinking: { type: 'disabled' }`（该模型下有效，不带时思考会吃光 `max_tokens`），`max_tokens: 4000`，经 `normalizeOpenAiRoles`。每次调用结束（成功、失败、中止）都写一行 `llm_requests`；**写账失败只记日志，绝不影响回复**。`MOCK_LLM=1` 时换成 `mock-llm.ts`（见下），不出网。密钥来自 `DEEPSEEK_API_KEY`；Runner 永远拿不到任何 LLM 密钥。

**运行循环**（`loop.ts`，目标 ≤300 行）：输入 = 代理、触发事件、会话、行事对象（`actingFor`：本人或他人）；组装系统提示 + 最近 40 条会话事件（转成 user/assistant 消息，代理自己的消息为 assistant，其余带 `【显示名】` 前缀为 user）→ 调模型 → 若有工具调用则执行并追加结果，继续 → 无工具调用时把文本作为 `message.posted` 落库。单次运行最多 8 次模型调用，超出则落一条"这件事步骤太多，我先停在这里"的消息并结束。流式文本经 `draft` 帧推送；落库后推 `event` 帧。

**调度**（`scheduler.ts`）：同一会话同一时刻只有一轮在跑；新的人类消息到来时，正在跑的代理完成当前这一步（模型调用或工具）后停止，然后从新消息开始新一轮。`POST /stop` 立即中止（`AbortController`）。

**谁该回应**：
- `dm`（本人与自己的一个代理）：代理总是回应。
- `dm`（两个真人，含双方分身）：按假设 2 触发对应的分身，被触发者以"为他人"身份运行；不满足条件时不启动任何代理运行。
- `group` 与含多个代理的会话：按假设 5 的轮次规则；轮到时代理可调用 `pass` 工具无声跳过。
- 代理自己发的消息不触发其他代理，只有轮次规则和 `delegate_to_teammate`、协商能让代理之间传话。
- 真人私聊里的分身按假设 2 触发；本人在私聊里的发言不触发自己的分身，但作为上下文出现在分身下一次运行里。
- 防循环：同一会话里没有新的人类消息时，代理之间的交接累计 ≥8 次就停止。因任何上限停止（轮次 4、交接 8、单次运行 8 次模型调用）时，都落一条 `agent.action{tool:'system', ok:false}`，summary 写明是哪个上限。

**行事对象与可用工具**：

| 工具 | 为本人 | 为他人 | 说明 |
|---|---|---|---|
| `pass()` | 群聊 | 群聊 | 无声跳过 |
| `memory_search(query, about?)` | 本人可见的记忆条目、画像与本人资料 | 按可见范围与类别授权过滤，第三人规则 | 见"记忆层"一节；无命中返回 `无结果` |
| `memory_save(title, body)` | ✓（默认 private） | ✗ | 写 notes，authorId=代理 |
| `delegate_to_teammate(handle, task)` | ✓ | ✓（只能交给同组专员，且专员同样处于"为他人"限制） | 同步调用专员一次运行，结果作为工具返回；深度 ≤2 |
| `escalate_to_owner(question)` | —（本人就在） | ✓ | 见 C3 |
| `create_commitment(title, dueAt?)` | ✓ | ✓（处理人=本人，requester=提问者） | 生成 commitment 待办 |
| `negotiate(personHandle, goal)` | ✓（仅 front） | ✗ | 见 C4 |
| `negotiation_reply(status, message, proposal?)` | 仅协商会话中 | — | 见 C4 |
| `device_list/read/write/exec` | ✓（仅绑定了 Runner 的代理） | ✗ | 见 R |

**系统提示**（`prompt.ts`）必须包含：代理身份（"你是{本人}的{代理名}，你是 AI，不是本人"）；`description`；为他人办事时追加 `delegationPolicy` 与三出口规则（能答就答并注明依据；超出授权调用 `escalate_to_owner`；涉及本人设为不可谈的话题直接拒绝）；可用工具说明；"用中文、简洁"。代理发出的消息在界面上一律带"某某的代理"标识，永不冒充本人。

**Mock LLM**（`mock-llm.ts`，e2e 与测试依赖它，必须确定性）：读取本次运行的触发文本（人类消息原文、上报答复原文或协商对方的上一步），按以下优先级：
1. 本次运行中已有工具结果 → 最终文本 `完成：<工具结果前 60 字>`，不再调工具。
2. 触发文本中的指令（第一个命中者生效）：`#pass`、`#delegate:<handle> <task>`、`#escalate <问题>`、`#note <关键词>`、`#remember <标题>|<内容>`、`#commit <标题>`、`#negotiate:<handle> <目标>`、`#ls <路径>`、`#read <路径>`、`#write <路径>|<内容>`、`#exec <命令>`、`#decide <标题>|<内容>`（record_decision）、`#api <METHOD> <path> <json>`（app_api_call）→ 调对应工具；`#claim` / `#claim-fix <问题>` 用于测试上报的运行时校验。记忆提炼时，材料里的 `#fact[:<handle>] <类别>|<内容>[|supersede]` 产出对应条目（见 mock-llm.ts 文件头）。
3. 群聊中，文本未 @ 本代理、也不含本代理 handle → `pass`。
4. 上报恢复运行时 → `本人答复：<答复原文>`。
5. 协商中：发起方第一步 `continue` + proposal `{"slot":"周四 15:00"}`；应答方看到 proposal 时，若协商目标含 `#needowner` 则 `need_owner`，含 `#reject` 则 `reject`，否则 `agree` 同一 proposal。
6. 其余 → `收到：<触发文本>`。
Mock 也要产生流式 `draft`（按 8 字切片）和 `llm_requests` 记录（tokens 按字数估算，`provider='mock'`）。

### 核心流程

**注册与代理组**：better-auth 注册 → 调 `/api/onboarding` → 事务内建 member、human principal、两个 agent principal（handle：`<handle>-twin`、`<handle>-ops`；显示名：`<本人>的分身`、`<本人>的执行助手`）及 agents 行。handle 规则 `^[a-z][a-z0-9-]{1,30}$`，租户内唯一，冲突 409。

**C1 和自己的代理组聊**：本人与自己的某个代理开 dm，或建群拉入多个自己的代理。发消息 → 事件落库 → 调度器触发代理 → `draft` 流式 → 回复落库。

**C2 真人互聊**：两人 dm 或多人群聊。没有代理成员的会话，服务端不启动任何代理运行。

**C3 别人找我的代理组（在同一个私聊里）**：
1. Bob 与 Alice 的私聊创建时，事务内把 Alice 的分身和 Bob 的分身都加为成员（role=member）。已有的真人私聊在迁移时补上双方分身。界面上分身不占会话标题，只在检查器的"分身"一栏列出。
2. 触发：Bob 发消息时，若消息 @ 了 Alice 的分身，或请求体 `askTwin: true`，或 Alice 的状态为 `busy`/`away`，则调度器触发 Alice 的分身；它以"为他人（Bob）"身份运行：可检索 Alice 的共享资料、可转给 Alice 的助手、可上报。反之亦然。
**上报的运行时校验**（模型会口头声称"已转给本人"却不调用工具，靠提示压不住，必须由运行循环兜住）：代理为他人办事时，若准备落库的最终回复含有"声称本轮已转交本人"的表述（转给、转交、已上报、报给本人、问过本人等，判定集中在一个函数里），而本轮运行没有调用 `escalate_to_owner`，则不落这条回复，追加一条系统提示让模型再走一步："你的回复说已经转交本人，但本轮没有调用 escalate_to_owner。需要本人决定就调用它；否则改写回复，不要说已经转交。"最多纠正 1 次；第二次仍如此时，落回复并记一条 `agent.action{tool:'system', ok:false}` 说明未上报。回复里提到"之前已转交"（指上一轮真实发生过的上报）同样适用：模型改写措辞即可通过。生效范围：本轮可用工具里有 `escalate_to_owner` 的运行（为他人、直接被问到、不在协商会话里）；本人答复后的恢复运行与被转交的运行不校验。判定函数在 `agent/escalation-claim.ts`，smoke 复用它。

3. 上报：`escalate_to_owner(question)` → 事务内建 `work_items(kind=decision, ownerId=Alice, requesterId=Bob, conversationId=这个私聊)`、在私聊里落 `escalation.created`（界面为卡片：Bob 看到"已转给 Alice 本人"，Alice 看到带答复框的待办卡片）→ 本次运行结束 → Alice 收到 `work_item` 推送。
4. Alice 在卡片上或"待办"页答复（可勾"存为共享资料"）或拒绝 → work_item 置 done → 落 `escalation.resolved` → 调度器以答复为触发恢复分身运行 → 分身在同一私聊里回复 Bob。
5. Alice 在任何时候都能直接在私聊里亲自回复；她的发言不触发她的分身。
6. 状态：人的主体有 `status: 'available'|'busy'|'away'`（默认 available），本人在头像菜单里切换；变化经 WS 推送，头像右下角显示状态点。

**C4 代理之间协商**：
1. Alice 对自己的分身说"和 Bob 约周四讨论预算"→ 分身调用 `negotiate('bob', 目标)`。
2. 服务端建 `conversations(kind=negotiation)`（它不出现在会话列表里），成员：两个分身（member）、Alice 与 Bob（observer）；同时在 Alice 与 Bob 的私聊里（没有则新建）落一条 `negotiation.started{ negotiationConversationId, goal }`，界面渲染为协商卡片：显示当前步数与状态，点开在抽屉里看每一步与 proposal，结束后卡片显示结果与两人的确认按钮。`negotiation = { initiatorAgentId, responderAgentId, goal, step: 0, maxSteps: 8, state: 'running'|'waiting_owner'|'ended', lastProposal? }`。在 Alice 原会话落 `agent.action`（"已发起与 Bob 的代理协商"）。
3. 两个分身轮流运行，**每次运行必须以一次 `negotiation_reply` 结束**（不调用则服务端视为 `continue` 且 message 取其文本）；每步落 `negotiation.step`。
4. 判定：对方以 `agree` 回应且 proposal 与上一个 proposal 深度相等 → `agreed`；任一方 `reject` → `rejected`；步数达 8 → `exhausted`；`need_owner` → state=`waiting_owner`，按 C3 第 3–4 步给该代理的本人建 decision 待办，答复后恢复同一代理。
5. 结束时落 `negotiation.ended`；若 `agreed`，给 Alice 和 Bob 各建一条 `confirmation` 待办（带 proposal）；两人都 confirm → 两条都 done，并在协商会话落 `confirmation.resolved` ×2；任一 reject → 另一条也置 cancelled。发起方分身在 Alice 的原会话里回一句结果摘要。

**R 设备 Runner**：
1. Alice 在"设备"页点"添加设备"→ 得到配对码（6 组 4 位，10 分钟一次性，库里只存哈希）。
2. 在她的电脑上：`bun run --cwd apps/runner start pair <配对码> --server http://localhost:8930 --name 我的MacBook` → 调 `/api/runners/pair` → 本地写 `~/.orgos/runner.json`（`{ server, runnerId, token }`，权限 0600；`ORGOS_RUNNER_HOME` 可改目录，测试用）。
3. `bun run --cwd apps/runner start serve --workspace <目录>` → 出站连 `/runner/ws?token=`（ws-bridge 照搬 wisp）→ 发 `hello` 声明四项能力 → 服务端置 online 并推 `runner` 帧。
4. Alice 把"执行助手"绑定到这台设备（PATCH runnerId）。之后执行助手为 Alice 办事时有 `device_*` 工具。
5. `device_list/read` 直接下发；`device_write/exec` 先建 `approval` 待办（显示设备名、能力、完整参数），代理运行挂起等待，最长 10 分钟；approve → 下发执行；deny 或超时 → 工具返回"本人拒绝/超时"。
6. Runner 执行：路径一律 `resolve(workspace, p)` 后校验仍在 workspace 内，否则返回错误；`shell.exec` 用 `Bun.spawn(['/bin/sh','-c',cmd], { cwd: workspace })`，60s 超时杀进程，输出合并截断到 64KB。设备离线 → 工具立即返回"设备离线"。

**规则**：
1. 我们自己的 `delegate_to_teammate` 改为创建 `engine=builtin` 的任务；专员的结果写入任务并作为工具结果返回——全系统只有"任务"一种交办形态。
2. 与外部助手的私聊中：若该会话有未结束（非 completed/failed/canceled）的任务，本人的新消息作为该任务的追问（继续同一外部会话）；否则创建新任务。卡片上有"新任务"按钮强制开新任务、"完成"按钮结束任务。外部 agent 一轮结束（ACP stopReason）后任务置 `input_required`；24 小时无活动自动 `completed`。
3. 外部助手只替本人干活：为他人时它不在可交办范围内（分身转交时不可选）。
4. ACP `session/request_permission` → 建 `approval` 待办（payload `{ taskId, runnerId, toolCall, options }`），任务置 `awaiting_approval`；本人选择的选项原样回给 agent；10 分钟未处理视为拒绝。
5. ACP 的 fs 读写请求限制在任务 workspace 内（与设备能力同一套路径校验）；terminal 请求等同 `shell.exec`，走审批（本人可在审批卡片上选"本任务内始终允许"）。
6. 7. 子进程环境：沿用 wisp `spawn.ts` 的三条铁律——看不到 runner token 与服务器地址、orgos 不注入任何 LLM key、stdio 用管道不用 PTY。

### 话题与运行记录（阶段一扩展，见 `decisions/0004`）

**数据模型**：
```ts

         isMain: bool, createdBy -> principals.id, archivedAt?, createdAt, lastEventAt }
         unique(conversationId) where isMain；每个会话建立时同事务建主线话题

        actingForId, engine: 'builtin'|'acp', state: 'running'|'completed'|'failed'|'canceled',
        startedAt, endedAt?, llmRequestIds: text[] (或经 llm_requests.runId 关联), summary? }
llm_requests 增加 runId?；task_logs 增加 runId?

```

**规则**：
1. 代理运行只读当前话题的事件（外加压缩摘要与近期工作简报）；触发规则、群聊轮次、上报、协商都按话题运转（上报卡片落在触发它的话题里）。
2. 外部 agent：每个话题一个 ACP 会话（主线也是一个）；S6b 的"会话内有未结束任务则追问"改为"消息发在哪个话题就进哪个话题的 ACP 会话"。
3. "转为任务"：把普通话题改为 kind=task 并建 tasks 行（目标取该话题最后一条本人消息或本人填写）；任务完成后话题保留、可继续聊（再次交办时新建任务或重开）。别人经分身交办、分身转交助手时，直接在目标私聊中新建 kind=task 的话题。
4. "转成群聊"：以该话题为起点建新群（标题默认话题名），复制话题历史为新群主线的前置只读引用（不复制事件，显示"来自 X 的话题"并可展开），原话题标记已转出。
5. 压缩：运行前估算上下文超过 `模型窗口 - 16k` 或未压缩事件 > 400 条时，先由同一模型生成结构化检查点写入 compactions，之后该话题的运行从检查点 + 其后事件开始；最近约 2 万 token 保留原文。
6. 近期工作简报：每轮在历史之后附上该代理过去 48 小时在其他话题与会话里的最后一句，最多 10 行、约 350 token；为他人办事时只列目标人可见的会话。
7. 群聊：加人时其分身自动入群、退群时一起退；群成员列表只列人，分身在检查器"分身"栏；已有群迁移补齐分身。
   群聊里某人 P 的分身 T 只在三种情况开口：(a) 消息 @ 了 T（发言者是 P 本人时为本人办事，否则为发言者办事）；(b) 消息 @ 了 P 且 askTwin=true；(c) 消息 @ 了 P 且 P 忙碌或离开。P 没被点名时，不论是否忙碌 T 都不开口；P 没有 @ 自己的分身时，P 的发言不触发 T。
8. pi / hermes 适配器：tenant_settings 增加 `allowUnsupervisedAdapters`（默认 false，租户 owner 可开）；为 false 时这两个适配器不出现在可选列表；创建时须勾选"我知道它不经审批、不限工作目录"。

```
鉴权：内部调用走进程内函数；外部调用只接受任务令牌（Authorization: Bearer 或 x-api-key），令牌绑定 tenant、principal 与该话题的外部会话（taskId 仅作计量归属，随话题当前的任务变化），外部会话关闭（话题归档、助手删除、设备吊销、闲置收回、进程退出）即失效；任务结束不使令牌失效，同一话题继续用同一外部会话
```
- 目标厂商支持入口协议时直通（只换 key、改写 model 字段）；不支持时做协议翻译，**流式与工具调用都要正确**（参考 Magpie 的实现处理边界情况）。
- 互转一律经网关内部的**统一中间结构**，不写两两转换器：每种入口协议一个"解析为统一结构"、每种上游协议一个"由统一结构生成"（请求与流式响应各一套）。统一结构覆盖：消息内容片段（文本、图片、工具调用、工具结果、推理内容）、工具定义、采样参数、流式事件（开始、文本增量、工具参数增量、结束原因、用量）。直通时不经统一结构，但计量与审计从同一套用量解析取数。
- 路由组：`order` 依次尝试（上一个 5xx/429/超时再试下一个）、`rotate` 每次轮换；一次请求内的切换各写一行 llm_requests。
- 计量只在网关一处：`agent/llm.ts` 改为调用网关的进程内入口，不再直连厂商。
- **不做订阅共享**：不把任何 CLI 的登录态转成可供他人调用的模型来源（违反各家条款）。

**外部 agent 的两种模式**：
- 企业模式（默认）：服务端为任务签发任务令牌并随 `acp_start` 下发；Runner 启动适配器时按适配器表里的注入规则设置环境变量或启动参数，把 agent 指向 `<server>/llm`，模型取该外部助手配置的 'provider/model'。**不修改用户的全局配置文件**（如 ~/.claude/settings.json、~/.codex/config.toml），只用本次子进程的环境变量或参数；各适配器的注入方式在施工时逐个核实并写进适配器表。
- 个人模式：不注入，agent 用设备上自己的登录；仅当租户 `allowPersonalExternal=true` 时可选。
- Runner 仍然不持有任何厂商 key；它只在任务期间持有任务令牌。

**界面**：导航轨底部本人菜单里，租户 owner 可进"模型"页：添加厂商（选预设 + 填 key，"测试"按钮对每种协议发一个最小请求并显示延迟）、选择开放的模型、路由组、租户默认模型、外部 agent 模式开关；代理组页每个代理（含外部助手）可选模型。

**验收**：测试内起假的上游（OpenAI 与 Anthropic 两种格式，含流式与工具调用）断言：三种入口 × 两种上游的直通与翻译都正确（文本、流式增量、工具调用参数、usage）；路由组 order 在上游 500 时切到下一个；任务令牌在任务结束后 401；key 不出现在任何接口响应与日志中（grep 断言）；我们自己的代理引擎经网关调用且 llm_requests 只写一行。真机：以 DeepSeek 的 Anthropic 兼容端点为上游，企业模式下用 claude-code 适配器完成一个小任务，llm_requests 中有 taskId 与费用。

### 记忆层（阶段一扩展，细则；见 `decisions/0004` 与架构总览）

**目标**：不需要对代理说"记住"。组织里发生的事自动沉淀成带出处的记忆；分身替别人回答时按"来源可见范围 ∩ 本人的类别授权"取用并附依据；本人能看到、更正、撤回分身对外说过的话。

**三层**：
- 第 0 层 · 证据（已有）：events、task_logs、work_items 的答复、协商结果、notes。
- 第 1 层 · 记忆条目（新增 `memory_items`）。
- 第 2 层 · 画像（新增 `memory_profiles`）：按人的"当前状态"页（按项目的画像留到阶段二）。

**数据模型**：
```ts
memory_items { id, tenantId, subjectId -> principals.id,     // 这条记忆关于谁（人，或 S7 起的部门）
               kind: 'fact'|'decision'|'commitment'|'progress'|'preference'|'relation',
               content: text,                                 // 提炼后的陈述句，不含原话引用
               category: text,                                // 取自类别表
               entities: jsonb,                               // [{ type:'person'|'project'|'customer'|'topic', name, principalId? }]
               scope: jsonb,                                  // { kind:'owner'|'participants'|'unit'|'tenant', principalIds?: [], unitId? }
               sources: jsonb,                                // [{ kind:'event'|'task_log'|'work_item'|'note', id, conversationId?, topicId? }]
               confidence: real, status: 'active'|'superseded'|'retracted',
               supersededById?, ownerCorrected: bool default false,
               createdByRunId?, validFrom: timestamptz, createdAt, updatedAt }
memory_profiles { id, tenantId, subjectId, subjectKind: 'person'|'project', projectKey?,
                  content: text (markdown), itemIds: uuid[], sections: jsonb /* [{ text, itemIds }] */, builtAt }
memory_jobs { id, tenantId, topicId, trigger: 'idle'|'compaction'|'task_end'|'resolution', status, runAfter, attempts, error?,
              eventId?,           // resolution 的答复或协商结束事件
              throughEventId? }   // 话题已提炼到哪条事件
disclosure_rules { tenantId, ownerId, category, allowed: bool, pk(ownerId, category) }   // 本人的类别授权
```
类别表只在 `packages/protocol` 一处：项目进展、排期与交付、技术方案、决定与口径、客户与商务、流程与制度、工作方式偏好、人员与分工、私人事务、薪酬、健康、家庭、人事评价、凭据与安全。**默认可对外**（宽松）：前八类；**默认禁止**：后六类（私人事务、薪酬、健康、家庭、人事评价、凭据与安全），本人可在"对外政策"页逐类开关。

**写入（提炼）**：
1. 触发：话题最后一条人类消息后 10 分钟无新消息（去抖）；话题压缩前（在 `apps/server/src/agent/context.ts` 调用 summarize 之前，被压缩的那段事件即材料）；任务结束；上报被答复或协商结束（这一类不调模型，直接写 kind=decision 条目，出处指向答复事件）。
2. 提炼由后台 `memory_jobs` 执行：用租户默认模型经网关调用（计量记在系统运行名下：`runs.agent_id` 为空，trigger 为 `memory_job:<id>` 或 `memory_profile:<人>`，不出现在运行接口里），输入为该话题自上次提炼以来的事件（含任务过程摘要），输出 JSON 条目列表；服务端逐条校验（kind、category 在白名单内，sources 必须是本批输入里真实存在的事件 id，否则丢弃）。
3. 去重与更新：同一 subject、同一 category、实体重叠且内容相近的已有 active 条目 → 由模型判定"新增 / 取代 / 忽略"；取代时旧条目 status=superseded 并链到新条目，不删除。
4. 可见范围由来源自动决定：本人与自己代理的会话 → owner（仅本人）；两人（含双方分身）私聊 → participants{两人}；群聊 → participants{当时的真人成员}；部门群 → unit；notes 按其 visibility 映射（private→owner、shared→tenant、unit→unit）。
5. 凭据清洗：写入前抹掉疑似密钥、令牌、密码（沿用 Lorca 的做法：API key、Bearer、JWT、私钥块、`password:` 值 → `«已抹去 N 字符»`）。

**读取（检索）**：
1. 统一工具 `memory_search(query, about?)` 取代 `knowledge_search`：先过滤，再打分。过滤 = 条目 status=active 且（为本人时：subject 或 scope 包含本人；为他人 R 时：scope 包含 R，或 scope 为 tenant，或〔subject 是本人且 category 在本人的授权内〕）；notes 作为第 0 层参与，只查分身本人的资料（为他人时只查其中共享的）。打分 = 关键词（中文按字二元组、英文按词）+ 实体匹配 + 时间衰减；先返回相关的画像段落，再返回条目，最多 8 条，每条带条目 id。
2. **第三人规则（硬性）**：为他人 R 回答时，若条目 scope 是 participants 且包含 R 以外、本人以外的人，只返回 content（已是提炼后的陈述），出处显示为"来自与同事的交流"，不返回人名、原话和会话链接；系统提示要求不得推测或透露来源。
3. 回答附依据：检索结果带 `[M:短编号]`，代理回复引用后落库时解析为 `payload.citations` 并从正文剥离（只认本轮检索给出过的编号）；界面在消息下显示"依据"小标签，悬停显示条目内容；有权看原始出处的人可点开跳转。没有依据时如实说明或上报，不许编。
4. 近期工作简报（S6d 已有）保留。

**本人的控制**：
- "记忆"页：浏览、搜索、编辑、撤回自己的条目（撤回 = status=retracted，并触发画像重建）；显示每条的出处与可见范围。
- "代答记录"页：列出分身替本人对他人的所有回答（谁问、答了什么、用了哪些依据）；每条可"不对"（填更正 → 写一条 ownerCorrected=true、仅本人可见的条目，取代本人勾选的被引用条目（`replaces`，缺省为全部被引用的本人条目），最高优先）或"不许对外说"（把被引用条目改为禁止类别或撤回）。
- "对外政策"页：类别开关 + 已有的自然语言政策。

**画像**：某 subject 新增或变更 ≥10 条、或每日一次，由模型把其 active 条目整理成 markdown（负责什么 / 在推进什么 / 最近定了什么 / 协作偏好），存 itemIds；检索时画像按同样的可见性规则裁剪（只拼接可见条目对应的段落，做法：画像按条目分段生成并记录每段的条目 id）。

**不做**：向量检索（预留 `embedding` 可空列不建索引）；读取本地 agent 的记忆文件；按人统计活动数据。

**验收**：
- 假模型下提炼确定性（mock 对 `#fact <类别>|<内容>` 形式的消息产出对应条目）。
- scope 推导四种来源各一例；类别授权过滤（默认禁止类不外露，本人开启后可外露）；第三人规则（bob 问 alice 的分身，alice 只在与 carol 的私聊里说过的"项目进展"→ 回答含该事实，不含 carol 的名字与原话；"薪酬"类 → 无结果）。
- 取代链与本人更正优先；撤回后不再被检索；画像只拼可见段落。
- 真实模型：演示数据里跑一次提炼，抽查 10 条条目的类别、可见范围、出处正确；林晓分身替许诺回答一个只在林晓与周野私聊里出现过的排期问题，附依据且不暴露周野原话。

### 组织结构与部门分身（阶段一扩展，见 `decisions/0002`）

**数据模型**：
```ts
principals.kind 增加 'unit'；check 约束改为：human ⇔ userId 非空且 ownerId 空；unit ⇔ userId 空且 ownerId 空；agent ⇔ userId 空且 ownerId 非空（ownerId 指向 human 或 unit）
org_units        { principalId pk -> principals.id (kind=unit), tenantId, parentId? -> org_units.principalId,
                   headId -> principals.id (human), charter: text default '', createdAt, updatedAt }
unit_memberships { unitId, principalId (human), role: 'head'|'member', isPrimary: bool, pk(unitId, principalId) }
notes.visibility 增加 'unit'：ownerId 为 unit 时可用，仅该单元成员可见
```

**规则**：
1. 建单元时事务内同时建它的分身：handle `<单元handle>-twin`，显示名 `<单元名>的分身`，role=front，ownerId=单元；并建一个"<单元名>"群聊（成员 = 单元成员 + 单元分身）。成员变动同步群成员。
2. 单元分身**可被本租户任何人直接私聊**（与个人代理不同）："问产品部"。在该私聊中它总是回应；对非成员以"为他人"身份运行，只能检索该单元 `shared` 资料；对成员可检索 `unit` 与 `shared`。
3. 单元分身的"本人"是单元负责人：`escalate_to_owner` 与协商中的 `need_owner` 都把待办交给负责人；负责人可在单元页改为"负责人 + 指定决策人"之一（本期只做负责人）。
4. 决策代理：单元的 `charter`（章程，负责人用自然语言写）作为该分身的对外政策；章程允许的事分身直接答复或决定，并调用新工具 `record_decision(title, body)` 写入单元资料（visibility=unit，authorId=分身）；章程之外上报负责人。
5. 记录：单元群里被 @ 时回应（群聊轮次规则照旧）；工具 `record_decision` 与 `memory_save`（为单元时写 unit 资料）用于沉淀；本单元成员在待办里答复的、与单元分身相关的上报结果，勾选"存为资料"时存为单元资料。
6. 协商：`negotiate` 的对象可以是单元 handle（单元与单元、个人与单元）；单元一方由其分身出面，need_owner 交给负责人。
7. 硬边界：单元分身不是任何人私聊的成员，不读成员私有资料，不提供按人统计的活动数据；成员在单元页能看到单元资料里所有提及自己的条目。
8. 权限：租户 owner 管理单元树与负责人；负责人改章程、管理成员、管理单元资料；成员可新增单元资料。

**接口**：
```
GET    /api/org                                   → { units: { unit, head, members, twin, parentId }[] }
POST   /api/org/units { name, handle, parentId?, headId }  → 201   // 仅租户 owner
PATCH  /api/org/units/:id { name?, headId?, charter?, parentId? } // owner；charter 也可由负责人改
POST   /api/org/units/:id/members { principalId, role?, isPrimary? } / DELETE /api/org/units/:id/members/:principalId
与单元分身建私聊：POST /api/conversations { kind:'dm', withPrincipalId: <单元分身> } 允许（AGENT_NOT_REACHABLE 的例外）
```

**与话题、记忆层的衔接**（S6d、S6e 之后补充；与上文冲突时以本段为准）：
1. 话题：与单元分身的私聊、单元群都照常有主线与话题；单元分身的运行上下文只读当前话题，近期工作简报只列提问人也在的会话。
2. 身份：单元分身在与某人的私聊里总是回应，总是"为提问人办事"（actingFor = 提问人），它的"本人"是单元；上报、`need_owner` 交给负责人，负责人答复后恢复分身。单元群里只在被 @ 时开口（前文群聊三条规则里的 (b)(c) 对单元不适用）。
3. 记忆可见范围：单元群的来源 scope = `{ kind:'unit', unitId }`；`scopeIncludes` 与 `visibilityFilter` 把 unit 范围解释为"该单元当前成员与该单元本身"，仍只在 `memory/access.ts` 一处实现。notes 的 `unit` 可见性同理：单元成员可见；单元分身为成员办事时可检索 unit 与 shared 单元资料，为非成员只检索 shared。
4. 单元的类别授权：`disclosure_rules.ownerId` 可以是单元，由负责人在单元页的"对外政策"里管理，默认值与个人相同；章程（charter）是单元分身的自然语言政策，放进它的系统提示。
5. 第三人规则扩展：unit 范围的条目呈现给非成员时，一律按第三人规则处理（抹去单元成员姓名，出处写"来自与同事的交流"）。
6. 提炼：单元群的材料可以产出 subject = 单元的条目（关于单元本身的决定、承诺、进展）；单元分身的上报被答复、单元参与的协商结束，写 subject = 单元的 decision 条目。`record_decision` 写单元资料（visibility=unit），同时写一条 subject = 单元、scope 为 unit 的 decision 条目，出处指向该资料。`memory_save` 在单元分身下写单元资料。
7. 负责人的控制：单元页里负责人可浏览、编辑、撤回 subject = 单元的记忆条目，并查看、更正单元分身的代答记录（复用记忆页与代答记录页的组件与接口，接口加可选的 `unitId`，服务端校验调用者是该单元负责人）。
8. 协商：`negotiate` 的对象可以是单元 handle，单元一方由其分身出面；协商会话的观察者是单元负责人。
9. 单元群的识别：`org_units.group_conversation_id` 指向单元群；单元群的成员只随单元成员变动，不能在群里直接加减人。
10. 以单元名义发起协商的只能是该单元成员（含负责人）；协商双方由同一个人拍板时直接拒绝。
11. 与单元分身私聊产生的记忆，可见范围为 participants{提问人, 单元}；单元分身之后为别人回答时按第三人规则抹去提问人。
12. 单元分身没有交办工具；单元页的"对外政策"只对负责人显示，章程对所有人可读。

**界面**：通讯录顶部显示组织树（单元 → 成员），单元行有"问<单元名>"按钮；单元页：负责人、成员、章程（负责人可编辑）、单元资料（成员可见 unit 级）、单元分身的最近决定；导航轨不新增入口。

**演示数据**：星河科技设 产品部（负责人林晓，成员陈安）、研发部（周野）、销售部（许诺）；各部门分身有写好的章程（例如产品部："需求排期问题可以按《Q4 路线图》直接答复；新需求插队必须问林晓"），各有 2–3 条单元资料与一条已记录的决定。剧本新增"C5 问部门"与"C6 部门之间协商"。

### 应用接口工具（阶段一扩展：代理调用软件本身的接口）

**目标**：本人可以直接指挥自己的代理操作 orgos 本身，例如"拉个群，把周野和陈安叫上，群名叫结算页联调"。代理的权限与本人完全相同，不弹确认卡；接口新增时自动进入代理的能力范围。

**做法**：
1. **接口目录**（`apps/server/src/agent/app-api/catalog.ts`）：为每个已注册的 REST 路由登记一行：method、path、一句中文用途、风险级别、入参 schema（直接引用 `packages/protocol` 里的 Zod schema，不重写）。风险级别：
   - `public_read`：公开信息，例如通讯录、组织树、模型列表；
   - `private_read`：本人私有数据，例如会话、事件、待办、记忆、任务；
   - `social_write`：别人看得到的写操作，例如建会话或群、加人、发消息、开话题、协商；
   - `self_write`：只影响本人，例如改状态、写资料、改记忆、自己的代理；
   - `admin_write`：租户管理，例如单元树、租户设置、模型厂商与路由组；
   - `excluded`：不开放给代理，包括登录鉴权 `/api/auth/*`、开发调试 `/api/dev/*`、签发凭据（设备配对码、配对）、`/ws`、`/runner/ws`、`/llm/*`、引导建租户。
2. **完整性测试**：遍历 Hono 应用实际注册的全部路由，断言每一条都在目录里，而且目录里没有不存在的路由。新增接口不登记，测试就失败。接口本身仍是唯一的真相，目录只补说明与风险级别。
3. **两个工具**：
   - `app_api_search(query)`：按关键词返回最相关的至多 8 个接口，包括 method、path、用途，以及由 `z.toJSONSchema` 生成的入参。这样整份目录不进系统提示。
   - `app_api_call(method, path, query?, body?)`：在进程内调用同一个 Hono 应用（`app.request`），返回状态码与响应体，响应体截断到约 4KB 并注明。
4. **身份**：
   - 进程内调用经 Hono 的 `env` 传入内部上下文，这个上下文只能在进程内构造，网络请求伪造不了。鉴权中间件据此把请求者设为代理的本人，照常做成员校验与 `scoped(tenantId)`；权限检查全部复用现有服务，与本人从界面操作时一致。
   - 同一上下文经 `AsyncLocalStorage` 标记"由哪个代理代办"。`services/events.ts` 写事件时，若有此标记，就把 `actorId` 记为代理、`onBehalfOfId` 记为本人。界面显示"林晓的分身代林晓拉了群"。这只在 events.ts 一处实现。
   - 每次调用落一条 `agent.action`，写明 method、path 与结果摘要，另记进运行日志。
5. **可用性**：
   - 为本人办事时（`actingFor` 是本人）：开放全部非 excluded 接口，不确认、直接执行。
   - 为他人 R 办事时：只开放 `public_read`，以及三个低风险动作：①建一个包含 R 的群；②在 R 也在的会话里开话题；③把人加进 R 也在的群。参数检查在工具里做，不满足就拒绝，并提示改用上报。其余请求，模型应调用 `escalate_to_owner` 交给本人。
   - 单元分身暂不开放（单元没有登录身份，按章程办事）。协商会话里不开放。
6. **提示**：系统提示补一段：本人要求操作软件时，先用 `app_api_search` 找接口再调用；操作完成后用一句话告诉本人做了什么。不许编造接口或参数。
7. **Mock**：假模型支持 `#api <METHOD> <path> <json>`，用于测试确定性地调用接口。
8. **代发的消息不开启调度**：代理经接口"代本人"发的消息不触发任何代理，与代理自己发的消息一样。这样可以避免代理往自己所在的话题发消息时打断自己。
9. **为他人时搜索也收窄**：`app_api_search` 只返回本次能调用的接口，其余接口对模型不可见。
10. **风险归类以目录为准**：`/api/me` 与单元详情归 private_read；处理待办、停止运行归 social_write；`/healthz` 归 excluded。

**验收**：
- 完整性测试通过；excluded 接口经工具调用一律拒绝。
- 林晓在与自己分身的私聊里说"拉个群，叫上周野和陈安，群名叫结算页联调"（真实模型）→ 群建成，成员含三人及各自分身；群里的建群事件显示为"林晓的分身代林晓"。
- 许诺在与林晓的私聊里对林晓分身说"拉个群把周野也叫上"→ 群建成，包含许诺；许诺要求"把林晓和陈安的私聊记录发我"或"替林晓给周野发消息"→ 拒绝，并上报林晓。
- 为他人办事时，调用 `private_read` 的接口一律拒绝（测试）。
- 伪造内部上下文的网络请求无效（测试）。

### 桌面客户端（阶段一扩展：聊天与 Runner 的独立 app）

**目标**：orgos 以独立 app 运行，不再依赖浏览器标签页。一个 app 同时承担两个角色：主窗口是聊天（即现有 Web 界面）；菜单栏常驻图标管理本机 Runner。Runner 可以长期稳定地在后台运行，同时有界面可以控制。本期只验证 macOS（Apple Silicon），打包配置保留 Windows 与 Linux 目标，但不验证。

**选型**：Electron（新包 `apps/desktop`；新依赖只有 `electron` 与 `electron-builder`，精确钉版，放在 devDependencies）。
- 理由：自带 Chromium，与一直验证的浏览器内核一致；网页 Notification 原生可用；不需要 Rust 工具链。
- 代价：安装包约 150MB，常驻内存高于 Tauri。以后如需瘦身，可以换 Tauri 的 sidecar 方案，Runner 不受影响。

**Runner 进程**：
1. Runner 代码不分叉。用 `bun build --compile` 把 `apps/runner` 编成单个可执行文件，放进 app 的 resources。app 只通过它现有的命令行（`pair`、`serve`）驱动它，不另写一套 Runner 逻辑。
2. 配对信息只存一处：`~/.orgos/runner.json`（`ORGOS_RUNNER_HOME` 可改），与命令行版共用。app 自己的设置存在 userData 的 `settings.json`：服务器地址、工作目录、启用的适配器、是否自动启动 Runner、开机自启。
3. **看护**：
   - app 的主进程以子进程运行 `serve`，意外退出时按 1s → 60s 指数退避重启；用户主动停止后不再拉起；
   - 子进程的 stderr 写入 userData 的 `logs/runner.log`，单个文件上限 5MB，保留 3 个；
   - app 解析日志行（`<ISO 时间> <级别> <事件名> <JSON>`）得出状态：已连接 / 断开重连中 / 已停止 / 未配对，以及正在执行的任务数。需要新的状态信号时，只在 Runner 的日志里加事件名，不另开通道。
4. **环境**：
   - 从 Dock 或开机自启拉起的 app 拿不到登录 shell 的 PATH，Runner 会因此找不到 `claude`、`codex`。启动时用登录 shell 解析一次 PATH，交给子进程；
   - 子进程带 `NO_PROXY=localhost,127.0.0.1`；
   - Runner 运行期间用 `powerSaveBlocker('prevent-app-suspension')` 防止 App Nap。
5. **退出**：关掉聊天窗口只隐藏，Runner 继续跑。从菜单栏选"退出 orgos"才会退出；若有进行中的任务，先在控制窗口里提示。

**界面**：
- **聊天窗口**：
  - 加载服务器地址（默认 `http://localhost:8930`；第一次启动显示一个输入服务器地址的页面）；
  - 只允许在该源内导航，外部 http/https 链接交给系统浏览器；
  - 单实例锁，记住窗口大小与位置；
  - 有标准的"编辑"菜单（复制、粘贴、撤销在 macOS 上依赖它）。
- **菜单栏图标**：
  - 图标显示 Runner 状态（已连接 / 重连中 / 已停止 / 未配对）；
  - 菜单项：打开 orgos、Runner 控制、启动 / 停止 Runner、开机自启（勾选项）、退出。
- **Runner 控制窗口**（app 自带的本地页面，不是 Web 应用的页面）：
  - 服务器地址；
  - 配对：输入配对码与设备名，调用 `pair`；
  - 状态：连接状态、最近连接时间、正在执行的任务；
  - 工作目录：用系统对话框选择；
  - 适配器：列出 protocol 里的适配器表，并用登录 PATH 检测本机是否已安装；
  - 启动 / 停止 / 重启；
  - 打开日志；
  - 解除本机配对：先确认，再删除本机的 `runner.json`；服务端的吊销仍在 Web 的设备页做。
  - 样式遵守 DESIGN.md：构建时引用 `apps/web/src/app/tokens.css`，不复制一份。
- **通知与角标**（Web 端的小改动）：
  - 新增 `apps/web/src/lib/desktop.ts`：页面在桌面壳里时（preload 暴露了 `window.orgosDesktop`），把未读总数交给 `setBadge`；
  - 窗口不在前台时，别人发给我的消息和我的待办用系统通知提醒，点通知打开对应会话；
  - 在普通浏览器里，这个文件什么都不做。

**安全**：
- `contextIsolation`、`sandbox` 开启，`nodeIntegration` 关闭；preload 只暴露白名单方法（setBadge、以及控制窗口所需的 Runner 操作）。
- 聊天窗口的权限请求只放行通知。
- Runner 令牌只由 Runner 自己读写，app 不读取 `runner.json` 里的 token 字段。

**命令**：
- `bun run desktop:dev`：对着已在运行的服务端开发；
- `bun run desktop:build`：编译 Runner 二进制，再打出 macOS arm64 的 `.app` 与 `.dmg`（未签名）。

**验收**：
- 门禁全绿；看护逻辑（退避、日志解析、PATH 解析、日志轮转）有单测。
- 打包出的 `.app` 启动后能登录聊天；关窗后菜单栏仍在。
- 在控制窗口配对一台 Runner（用临时的 `ORGOS_RUNNER_HOME`），服务端设备页显示在线；杀掉 Runner 子进程后自动重启并恢复在线；停止后显示离线。
- 窗口在后台时，别人发来的消息弹出系统通知，Dock 角标显示未读数。

### 决策待办的候选选项（阶段一补充）

**目标**：需要本人拍板的待办（上报、协商中的 need_owner）不只给一个空的答复框，还给出分身整理好的 2–4 个候选答复，本人点一下即可答复；也可以自己写。

1. **协议**：
   - decision 待办的 payload 增加可选 `options: string[]`（2–4 条，每条 ≤ 60 字）；
   - `ResolveWorkItemRequest` 的 answer 增加可选 `option: number`，表示选的是第几个候选；自己写的就不带；
   - `escalation.resolved` 事件记下 `option`；
   - 只增不改：没有 options 的旧待办照常可用。
2. **工具**：
   - `escalate_to_owner` 增加可选参数 `options`。工具说明要求：问题有明确的几种答法时（同意 / 不同意 / 折中，或几个具体日期、价格），给出候选，每条是可以直接转告对方的完整答复；
   - 协商的 `negotiation_reply` 在 status=need_owner 时同样可带 `options`（例如"接受对方的 10 月 9 日 14:00""改约 10 月 10 日上午""不约了"）。
   - 服务端整理候选只在 `services/work-items.ts` 的 `decisionOptionsOf` 一处：去空白与重复；超过 60 字的整条丢弃（截断会把一句答复截坏）；多于 4 条只留前 4 条；不足 2 条则不带候选。
   - `option` 是候选下标（从 0 起）；带 option 时答复文字必须与该候选一致，否则 400。候选同时写进待办与 `escalation.created`。
3. **界面**：
   - 决策表单（会话里的上报卡片与待办页共用）在答复框上方列出候选，每项一个可选中的按钮；
   - 选中后答复框填入该候选，仍可再改；改过之后按"自定义"处理，不带 option；
   - 最后一项固定为"自己写"，点了清空答复框并聚焦；
   - "存为资料""暂不答复"保持不变；
   - 键盘可操作，数字键 1–4 选择候选。
4. **Mock**：`#escalate <问题>|<候选1>|<候选2>…` 产出带候选的上报。
5. **验收**：
   - 测试：带候选的上报在待办接口里可见；选候选答复后事件记下 option，分身转告的正是该候选的文字；自定义答复不带 option；候选条数超过 4 条时截断。
   - 真实模型：许诺问林晓的分身"大客户 A 要 85 折，能答应吗"，上报待办带 2–4 个合理候选。

### Runner 配对的提示（阶段一补充）

1. `pair` 成功后多打印一行下一步："启动：bun run --cwd apps/runner start serve --workspace <工作目录>，或在桌面客户端里启动"。
2. 配对失败且本机已有 `runner.json` 时，在错误信息后提示："这台电脑已配对（服务器 <server>），无需重复配对；配对码只能用一次。"不读取、不打印 token。
3. Web "设备"页的配对面板把命令分两步展示：第 1 步 pair，第 2 步 serve，并说明也可以在桌面客户端的 Runner 控制里填配对码。

### 客户端即 Runner（阶段一补充，覆盖"桌面客户端"一节里手动配对的部分）

**目标**：桌面客户端装在哪台电脑上，那台电脑就自动成为当前登录账号的一个 Runner，不需要手动输入配对码。单独的命令行 Runner 只用于没有安装客户端、只作为 Runner 使用的机器。

1. **自动配对**：
   - 客户端里的 Web 页面（通过 `lib/desktop.ts`）在登录后读取本机 Runner 的身份：preload 暴露 `runnerIdentity()`，返回 `{ paired, server, runnerId }`。app 只读 runner.json 的 server 与 runnerId 两个字段，不读 token。
   - 以下任一情况需要配对：本机未配对；配对的服务器不是当前页面的源；runnerId 不在当前账号的 `GET /api/runners` 列表里（例如换了账号登录）。
   - 需要配对时，页面用本人的登录身份调用 `POST /api/runners/pairing-codes` 拿到一次性配对码，交给 preload 的 `pairRunner(code)`；主进程用现有的 `pair` 命令配对（设备名取本机名），配好后自动启动 `serve`。
   - 配对码只在这一次流转中出现，不落盘、不进日志。
2. **默认工作目录**：`~/orgos-workspace`，不存在时创建。控制窗口里仍可改。代理的读操作限于工作目录；写文件、执行命令照旧要本人审批。
3. **开关**：
   - "本机作为 Runner"默认开启。在菜单栏和控制窗口里都可以关闭，关闭后停止 Runner，并且不再自动配对；设置存在 app 的 settings.json。
   - 手动输入配对码的入口保留，放到控制窗口的"高级"里。
4. **换账号**：新账号登录后，本机改配对到新账号。旧账号那条设备记录保留为离线，由旧账号在"设备"页删除。客户端不代替旧账号吊销。
5. **来源标记**：配对请求可选带 `via: 'desktop' | 'cli'`（协议只增不改），存进 runners 表。Web "设备"页据此区分"桌面客户端"与"独立 Runner"；页面在客户端里打开时，本机那台标记为"本机"。
6. **启动顺序**：app 启动时，只要本机已配对到当前设置的服务器就立即启动 Runner，不等聊天窗口登录（窗口隐藏时 Runner 也在后台运行）。
7. **在普通浏览器里**：以上都不发生，`lib/desktop.ts` 什么也不做。
   实现补充：`runnerIdentity()` 另带 `enabled`（开关关闭时页面不申请配对码）；开关重新打开时主进程经 `onRunnerEnabled` 通知页面重新检查；原"自动启动 Runner"并入"本机作为 Runner"一个开关；设备名在 macOS 取系统"电脑名称"（`scutil --get ComputerName`），失败回退到主机名；桌面与 Web 之间的桥接类型只在 `packages/protocol/src/desktop.ts`。
8. **验收**：
   - 测试：页面侧"是否需要配对"的判断是纯函数，未配对、服务器不同、runnerId 不属于本人三种情况都要覆盖；pair 请求带 via；设备列表返回来源。
   - 打包实测：新装的客户端（临时 userData 与临时 `ORGOS_RUNNER_HOME`）登录林晓后，无需任何操作，服务端设备页出现"<本机名>"（桌面客户端）且在线；退出登录后改登周野，本机改配对到周野，林晓名下那台显示离线；关闭"本机作为 Runner"后显示离线，也不再自动配对。

### 消息格式：纯文本、Markdown、HTML（阶段一补充）

**目标**：消息支持三种格式：`text`（纯文本）、`md`（Markdown）、`html`。模型的回复多是 Markdown，要正确渲染。

1. **协议**：`message.posted` 的 payload 增加可选 `format: 'text' | 'md' | 'html'`，缺省按 `text` 处理（只增不改，旧消息不变）。`PostMessageRequest` 增加可选 `format`。
2. **谁发什么**：
   - 内置代理的回复一律记为 `md`；外部助手（ACP）的文字也记为 `md`。
   - 人发的消息默认 `text`；输入框提供一个"Markdown"开关，打开后记为 `md`。这个开关的状态按人记在浏览器本地。
   - `html` 只允许代理与接口调用产生：人通过输入框不能发 html；经应用接口代发的消息可以带 html。
3. **渲染**：
   - `text`：保持现状（保留换行，@提及渲染成标签）。
   - `md`：用 `react-markdown` + `remark-gfm` 渲染，这是新增的两个运行时依赖，精确钉版。
     - 不渲染内嵌的原始 HTML。
     - 链接在新窗口打开，并带 `rel="noopener noreferrer"`。
     - 图片只显示为链接，不自动加载外部图片。
     - @提及在 md 里同样渲染成标签。
     - 代码块用等宽字体并可横向滚动，本期不做语法高亮。
     - 表格可横向滚动。
     - 样式全部用 tokens.css 的变量，与 DESIGN.md 的正文层级一致，不引入 typography 插件。
   - `html`：放进 `<iframe sandbox="allow-same-origin allow-popups allow-popups-to-escape-sandbox" srcdoc=…>` 渲染，不给 `allow-scripts`，所以任何脚本都不执行。
     - 父页面在加载后读取文档高度并设置 iframe 高度，上限 600px，超出则 iframe 内滚动。
     - 注入一段基础样式（字体与颜色跟随当前主题）。
     - 链接在新窗口打开。
4. **其他出现消息正文的地方**：会话列表的最近一条预览、系统通知、搜索摘要、记忆提炼材料，一律使用纯文本。md 去掉标记符号，html 取文本内容，由一个共享的 `plainTextOf(payload)` 函数完成，只写一处。代理的历史上下文与触发消息例外：text 与 md 原样给模型（保留标记，让模型延续格式），只有 html 经 `plainTextOf` 转成纯文本。
5. **提示**：代理系统提示里说明"回复用 Markdown，简洁，少用标题"。
5a. **代理回复 HTML**：新工具 `post_html(html, summary)`，把一条 html 消息发在本次运行所在的话题里。
   - `summary` 是一句话摘要，不超过 60 字，用于列表预览与通知；`plainTextOf` 对 html 取文本时，优先用这个摘要。
   - `html` 上限 50KB。服务端去掉 `<script>`、`<iframe>`、`<object>`、`<embed>`、`on*` 事件属性与 `javascript:` 链接。沙箱本来就不执行这些，这里再清理一遍，让存进库里的内容也干净。
   - 可用范围：为本人或为他人办事都可以；协商会话里不可用。
   - 调用后本次运行照常结束：模型不再另发文字；若另发，就作为 md 跟在后面。
   - 系统提示补一句：对方要"能直接贴进邮件的版本""排版好的报告或卡片"这类成品时，用 post_html，只用内联样式，不引用外部资源；日常回复仍用 Markdown。

## 边界情况

| 情况 | 期望行为 |
|---|---|
| 未登录访问 /api 或 /ws | 401 / WS 以 4401 关闭 |
| 访问其他租户的会话、待办、代理、设备 | 404 |
| 非成员读取同租户的会话 | 404 |
| 单独与他人的任何代理（分身或助手）开私聊 | 400 `AGENT_NOT_REACHABLE`（找别人的分身请在与他本人的私聊里点名或切"问分身"） |
| 删除分身 | 403 |
| 消息空或超 8000 字 | 400 |
| 同一对人重复建 dm | 返回已有会话 200 |
| 代理运行中又来人类消息 | 当前步完成后停止，新一轮从新消息开始；不出现两个代理运行同时写同一会话 |
| DeepSeek 超时/5xx/限流 | 重试 2 次（1s、3s）；仍失败落 `agent.action{ok:false}` 与一条"模型暂时不可用"消息；`llm_requests` 记 httpStatus |
| 计量解析失败 | `parseError=true`，tokens 为空，回复照常 |
| 代理之间来回超过 8 次无人介入 | 停止并记录原因 |
| 协商对方代理的本人不在同租户 | `negotiate` 工具返回"找不到此人"，不建会话 |
| 待办重复处理 | 409 |
| 上报后本人长时间不答复 | 待办一直 open；提问方会话保持"已转给本人"状态 |
| 配对码过期或已用 | 400 `PAIRING_CODE_INVALID` |
| Runner token 被吊销 | 立即断开 4003；之后连接 401 |
| Runner 断线重连 | 退避重连后重新 hello；执行中的 job 在服务端 60s 超时后返回失败 |
| 设备路径越界（`../`、绝对路径指向 workspace 外、符号链接逃逸用 realpath 校验） | 返回错误，不读写 |
| 命令输出超 64KB | 截断并在末尾注明"已截断" |
| 同一设备同时收到多个 job | 并行执行，按 jobId 回结果 |
| 代理为他人办事时尝试设备工具或私有资料 | 工具不在可用列表；即便模型编造调用，也返回"无权限" |
| 浏览器 WS 断开重连 | 前端按每个会话已知的最大 seq 调 `events?after=` 补齐 |

## 验收标准

机器关（每条独立运行，看真实退出码，不接管道）：

1. `bun install && bash scripts/dev-db.sh && bun run db:migrate` 退出码 0；重复执行 `dev-db.sh` 仍为 0。
2. `bun run typecheck`、`bun run lint`、`bun run test` 各自退出码 0；集成测试连真实 Postgres（`orgos_test`）。
3. `MOCK_LLM=1 bun scripts/e2e.ts`（即 `bun run e2e`）退出码 0。脚本自建库 `orgos_e2e` 并迁移，以子进程起服务端于 8931（不起 Next），自建两个租户与用户（alice 为"测试公司"owner，bob、carol 加入；dave 属"别家公司"），结束后停进程、删库、删临时目录；每个场景逐项打印"✓ 场景 · 子项"，失败时打印期望与实际并以非 0 退出。逐项断言：
	- **C2**：alice 与 bob dm 互发各一条，双方 WS 均收到 `event`；此时该会话 `llm_requests` 行数为 0（没有代理运行；记忆提炼要等话题 10 分钟无新消息）。
	- **C1**：alice 对自己的分身发"你好"→ 收到至少一个 `draft` 帧与一条来自分身的 `message.posted`，正文为 `收到：你好`；发 `#delegate:alice-ops 整理周报` → 出现 `agent.action`（tool=delegate_to_teammate）且最终回复以 `完成：` 开头，并产生一条 engine=builtin、completed 的任务；发 `#remember 私事|下周三请假看牙` 后 notes 多一行 authorId=分身、visibility=private。
	- **群聊轮次**：alice 建群含分身与执行助手，发 `@alice-ops 你好` → 只有执行助手回复，分身无消息（群聊里分身只在被 @，或其本人被 @ 且问分身 / 本人忙碌时开口）。
	- **C3**（全部在 alice 与 bob 的同一个私聊里；`#note` 调 `memory_search`，本人的资料作为第 0 层参与检索）：alice 建共享资料"Q4 预算口径：不含税"；alice 状态为 available 时 bob 发 `#note 预算`（不带 askTwin）→ 该会话 5 秒内没有任何代理消息；bob 以 `askTwin:true` 发 `#note 预算` → alice 的分身回复以 `完成：` 开头且含"不含税"；bob 以 `askTwin:true` 发 `#note 看牙` → 回复含"无结果"且不含"请假"（私有记忆不外泄）；alice 本人对自己的分身（她与分身的私聊）发 `#note 看牙` → 回复含"请假"；alice 把状态设为 busy，bob 直接发 `#escalate 交付能否提前到 10 月 1 日`（不带 askTwin）→ 私聊里出现 `escalation.created`，alice 的 `GET /work-items` 有一条 decision；alice 以"可以"答复并勾选存为资料 → 私聊里出现 alice 分身的 `本人答复：可以`，notes 多一条 shared；bob 的分身在整个过程中没有发任何消息；alice 自己在私聊里发 `#note 预算` → 不触发任何代理。任何人以别人的分身或助手为对象建私聊 → 400 `AGENT_NOT_REACHABLE`。
	- **C4**：alice 对自己的分身发 `#negotiate:bob 约周四讨论预算` → 出现 kind=negotiation 会话且它不在两人的 `GET /api/conversations` 列表中，alice 与 bob 的私聊里有一条 `negotiation.started`；`negotiation.ended.outcome='agreed'`，proposal 为 `{"slot":"周四 15:00"}`；alice 与 bob 各有一条 confirmation 待办；两人 confirm 后两条均为 done。再发一次目标含 `#needowner` 的协商 → bob 收到 decision 待办，答复后协商继续并结束。目标含 `#reject` → outcome=`rejected`，无 confirmation 待办。
	- **R**：用临时目录作 `ORGOS_RUNNER_HOME` 与 workspace，脚本以子进程执行 runner 的 pair 与 serve；alice 把执行助手绑定到该设备，之后以下指令都由 alice 发给自己的执行助手（dm）：`#ls .` 得到目录列表，无待办产生；发 `#exec echo hi` → 产生 approval 待办，approve 后回复含 `hi`；再发 `#exec echo no` 并 deny → 回复含"拒绝"；发 `#read ../../etc/passwd` → 回复含"超出工作目录"且未读到内容；bob 在与 alice 的私聊里问 alice 的分身 `#exec echo x` → 回复含"无权限"，且不产生 approval 待办；吊销设备后 runner 子进程连接被关闭（4003），其重连握手被拒（HTTP 401）。
	- **租户隔离**：dave 请求 alice 的会话、待办、代理、设备各返回 404；dave 的 `/api/directory` 不含 alice；dave 找 alice 的代理（用 alice 分身 id 建 dm）返回 404。
